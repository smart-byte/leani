The cursor in a Leani change envelope is an opaque resume and acknowledgement
token. Store it beside the application state derived from that change. The
destination transaction is the durable boundary; the later Leani
acknowledgement advances retention and delivery state.

<Steps>
1. Create a stable named consumer once, or inspect the existing consumer after a
   restart.
2. Poll retained changes under a lease.
3. Apply one change idempotently and store its cursor in the same destination
   transaction.
4. Commit the destination transaction.
5. Acknowledge that cursor to Leani. If this request is lost, accept the same
   change again and rely on idempotent application.
</Steps>

<Aside type="danger" title="Never acknowledge before your commit">
  An early acknowledgement can make Leani eligible to discard history your
  application has not durably applied. A failed acknowledgement after commit is
  safe: the event may be delivered again, so application writes must be
  idempotent.
</Aside>

The consumer's credential goes with every call, and Leani accepts an
acknowledgement only for a change it delivered to that consumer. This loop
uses the generic consumer routes, which serve processors with `canonical`
delivery ordering. A processor with a split live stream
(`block_versioned_idempotent`, such as `blobs-money`) fences renewal and
acknowledgement by streaming session: read it with the SDK's
`streamLive()` or `subscribe()` from `@smart-byte/leani-sdk/backfill`, and
acknowledge each batch's boundary.
