The primary first run indexes a bounded Ethereum Mainnet range from the public
Xatu dataset. It needs no provider credentials, produces decoded application
data you can query, and keeps the requested work and storage boundary explicit.

<Aside type="caution" title="Previewing before v0.1.0 is published">
  The release commands below become runnable when the matching GitHub tag,
  Homebrew formula, container, and crate are published. Until then, use a local
  source checkout and its `config/modes/windowed.toml`; do not replace the
  pinned version with an arbitrary remote `main` build.
</Aside>

<Steps>
1. Install a release binary for your platform, use Homebrew from the `leani-dev`
   tap, or build the workspace with Cargo.
2. Save the selected profile as `./leani.toml` and run `leani doctor`.
3. Index one bounded public-data range and inspect its decoded output and exact
   coverage.
4. Query `/v1/capabilities` and `/v1/processors` instead of assuming the node was
   compiled and configured with a particular processor.
5. Use the offline fixture only when you need to isolate packaging/runtime
   health from network-source behavior, then attach a consumer.
</Steps>

<Aside type="caution" title="The data directory is part of the configuration">
  Processor identity, schema compatibility, retained change history, and
  checkpoints are durable state. Do not point two independent nodes at the same
  writable directory or casually reuse a production directory for experiments.
</Aside>

## What you can install

<CardGrid>
  <Card title="Release binary">
    Best for a pinned, auditable deployment. Verify the published checksum before
    starting the binary.
  </Card>
  <Card title="Homebrew">
    Convenient on macOS and Linux through the `leani-dev` namespace once the
    release formula for your version is published.
  </Card>
  <Card title="Cargo">
    Useful for contributors and processor authors working against the workspace.
    A source build is not the same artifact as a signed release binary.
  </Card>
</CardGrid>

Choose the smallest path that proves the boundary you care about:

- [Install a pinned release](/docs/getting-started/install/) and verify its identity.
- [Index a bounded Mainnet range](/docs/getting-started/bounded-mainnet/) and inspect exact coverage.
- [Prove it offline](/docs/getting-started/offline-proof/) when diagnosing an installation without network access.
- [Attach a durable consumer](/docs/getting-started/first-consumer/) with commit-then-ack semantics.
- Use the [complete quickstart](/docs/getting-started/offline-to-mainnet/) when you want the native and Docker flows on one page.
